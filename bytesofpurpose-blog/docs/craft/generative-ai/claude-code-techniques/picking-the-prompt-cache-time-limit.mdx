## What annoyed me

Do you use Claude Code with an API key? If so, this page is for you.

At work we access Claude, but not through the monthly subscription. Instead, we get a bucket of API
tokens. After burning through my bucket a couple of times, I compared it with my personal $200 a
month Max plan. To match what that plan gives me, I'd need about $7,000 a month in credits. I figured tokens were just more expensive.

Then I came across [a thread on r/ClaudeAI](https://www.reddit.com/r/ClaudeAI/comments/1w8p8tn/prompt_cache_ttl_when_does_1_hour_beat_the/)
arguing that anyone who pauses 15 to 45 minutes between turns should switch the prompt cache from
its 5-minute default to 1 hour. The reasoning was neat: the 1-hour cache costs more to fill, but
one return after a coffee break pays that back. I pause like that all day. I step away while a long
task runs, I sit in a meeting, I keep two or three sessions open and hop between them.

But I had no idea what my pauses really looked like, or which limit Claude Code was even using for
me. I was about to change a setting on the strength of a hunch.

## What I did about it

I read the docs to find out which limit applies when, then had Claude measure every pause in my own
session logs and work out what each limit would have cost. The answer surprised me twice. On my
subscription it is a wash. At work, on API credits, 1 hour would have saved about a tenth, nearly
all of it in my long sessions. Then I built the three calculators below so you can try your own
pattern before you change anything.

**The technique:** pick the prompt cache's time limit to fit how you work, and measure your pauses
before you pick.

## What the cache holds

Every request Claude Code sends starts with the same block of text: the system prompt and tool
definitions, then your `CLAUDE.md`, memory and rules, then the conversation so far. The
[prompt cache](https://code.claude.com/docs/en/prompt-caching) keeps that block on Anthropic's side,
so the next request can read it back at a small fraction of the input price instead of paying full
price to send it again. Each turn adds to the end, so the block grows all session.

<ContextSim />

If the cache is still there, a turn pays a small read price for everything before it and the
write price only for what it adds. If the cache has expired, the whole block is written again at
full write price. In a long session that block is easily over 100k tokens.

## The two time limits

The cache lives 5 minutes by default. Every time a request reads it, the clock restarts, so a fast
back and forth keeps it warm for free. You can ask for 1 hour instead. The catch is the price of
writing:

| Model | Input | Write, 5-minute cache | Write, 1-hour cache | Read from cache |
|---|---|---|---|---|
| Opus 5.5 | $4 | $5 | $8 | $0.20 |
| Sonnet 5.5 | $2 | $2.50 | $4 | $0.10 |
| Fable 5.1 | $10 | $12.50 | $20 | $0.25 |
| Opus 4.5 to 5 | $5 | $6.25 | $10 | $0.50 |
| Sonnet 4.5 / 4.6 | $3 | $3.75 | $6 | $0.30 |
| Haiku 4.5 | $1 | $1.25 | $2 | $0.10 |

*Dollars per million tokens, from [Anthropic's pricing page](https://platform.claude.com/docs/en/about-claude/pricing), October 2026.*

A 5-minute write costs 1.25x the input price and a 1-hour write costs 2x, on every model. So the
1-hour cache costs an extra 0.75x on every token it writes. It earns that back when you return after
a pause of 5 to 60 minutes: the 5-minute cache is gone and would write the whole block again at
1.25x, while the 1-hour cache reads it back. On most models a read is 0.1x, so that return saves
1.15x. On Opus 5.5 and Sonnet 5.5 reads are 0.05x and on Fable 5.1 they are 0.025x, so a return
saves even a bit more. One return after a 5 to 60 minute pause covers the extra on the same tokens.
Past an hour, both caches are gone and the 1-hour one has only cost you more.

A pause isn't only you stepping away. When Claude hands a job to a subagent and waits for it, the
subagent works in its own conversation, so the main one sends nothing until it comes back. A
subagent that takes 5 to 60 minutes is a coffee break as far as the main cache is concerned. One
that comes back in under 5 minutes costs nothing either way, and one that takes over an hour finds
both caches gone.

## What a whole session costs

The rule above is per token, and a session keeps adding tokens. Every turn pays the 0.75x extra on
what it adds, and only the turns after a 5 to 60 minute pause get the saving back. That gives one
number to watch: the tokens read back after those pauses, as a share of everything the 1-hour cache
writes. Above about 63% (65% on older models), 1 hour wins. Below it, 5 minutes wins.

<CostSim />

With the starting settings (Opus 5.5, a 22k start, 8k per turn, 30 turns, one 20-minute break at
turn 15), the break re-reads 54% of what gets written and the 5-minute cache is slightly cheaper.
Move the break later, or add a second one, and 1 hour wins: a return late in a long session
re-reads almost everything written before it. Make the breaks longer than an hour and 5 minutes
always wins.

## What my own logs said

*Measured October 21 to 28, 2026. List prices, main conversation only.*

I had Claude write a small script that reads my Claude Code session logs, sorts every request by
time and puts the pause before each one into one of three groups: up to 5 minutes, 5 to 60 minutes,
and over an hour. Then it works out what the same requests would have cost on the other limit. Only
totals come out.

I ran it twice: on my personal Macs, where I use a subscription, and on my work Macs, where I use
API credits.

### On my subscription: about even

- **I was already on 1 hour.** A subscription gives the main conversation 1 hour and subagents 5
  minutes, and my logs show exactly that split.
- **I hardly ever pause.** 98% of my requests came within 5 minutes of the one before. Most
  requests are Claude working through a task, not me.
- **Most of my middle pauses aren't me.** I ended only 43% of the 5 to 60 minute pauses by typing.
  Tools, background jobs and subagents ended the rest, and subagents came back in under 5 minutes
  86% of the time.

| Pause before a request | All time | Last 30 days |
|---|---|---|
| Up to 5 minutes | 210,179 (98%) | 52,945 (98%) |
| 5 to 60 minutes | 3,385 (1.6%) | 948 (1.8%) |
| Over an hour | 1,202 (0.6%) | 191 (0.4%) |

A 5-minute cache would have saved 2% all time and cost 2% more in the last 30 days. For me, on a
subscription, the limit doesn't matter.

### At work, on API credits: 1 hour would have saved about a tenth

On an API key the main conversation runs at 5 minutes. I took the 96 work sessions whose main
conversation clearly ran at 5 minutes, about 26% of my work spend. With a 1-hour cache they would
have cost **9% less all time, and 21% less in the last 30 days.**

The saving isn't spread evenly. It sits in the long sessions where I kept coming back:

|---|--:|--:|---|
| 10 or more pauses of 5 to 60 minutes | 27 | 90% | 11% cheaper |
| Fewer than 10 | 37 | 10% | 2% dearer |

The other 32 sessions cost under $1 each: one question, one answer, done. 1 hour writes their

### The result

The same setting came out even on my subscription and about a tenth cheaper at work. The difference
is the pauses. My heaviest work sessions each had 10 or more returns after a 5 to 60 minute pause,
and on a 5-minute cache every one of those returns writes the whole conversation again. A 1-hour
cache isn't the whole gap between my work credits and my subscription. But on an API key it's one
setting, and my long sessions say it pays.

## Set it up

**Check which limit you're on.** In Claude Code 2.1.251 or later, `/usage` shows a "Prompt cache
(main)" line with your hit ratio, how many times the cache was missed, and whether it is still warm.
For which limit you're on, send one message and look at the usage:

```bash
claude -p "hello" --output-format json
# look for usage.cache_creation.ephemeral_1h_input_tokens and ephemeral_5m_input_tokens
```

**Which limit applies by default** ([Claude Code docs](https://code.claude.com/docs/en/prompt-caching)):

- Main conversation on a Claude subscription, within your plan: 1 hour.
- Main conversation on an API key, a cloud provider, or usage credits: 5 minutes.
- Subagents, compaction and other helpers: 5 minutes. On a subscription, a few helper requests
  that Anthropic's servers control get 1 hour.

**Change it** in `~/.claude/settings.json` (Claude Code 2.1.242 or later):

```json
{
  "promptCacheTtl": "1h",
  "subagentPromptCacheTtl": "5m"
}
```

or for one shell with `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` and `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=5m`.
`FORCE_PROMPT_CACHING_5M=1` overrides everything. The full order is on the
[prompt caching page](https://code.claude.com/docs/en/prompt-caching) and the keys are in the
[settings reference](https://code.claude.com/docs/en/settings).

**Calling the API yourself?** Ask for 1 hour on the block you cache:
`"cache_control": {"type": "ephemeral", "ttl": "1h"}`. See
[prompt caching in the API docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

**Measure your own pauses.** Claude Code keeps each session as a `.jsonl` file under
`~/.claude/projects/`. This counts the pause before every request, across all your sessions
(it needs `jq`):

```bash
for f in ~/.claude/projects/*/*.jsonl; do
  jq -rs '[.[] | select(.type == "assistant" and .message.usage)]
    | unique_by(.message.id)
    | map(.timestamp[:19] + "Z" | fromdateiso8601) | sort | .[]' "$f" 2>/dev/null |
  awk 'NR > 1 { g = ($1 - p) / 60; if (g <= 5) a++; else if (g <= 60) b++; else c++ }
       { p = $1 } END { print a + 0, b + 0, c + 0 }'
done | awk '{ a += $1; b += $2; c += $3 }
  END { printf "up to 5 min: %d\n5 to 60 min: %d\nover 60 min: %d\n", a, b, c }'
```

The log format isn't documented, so check it still works after an update. If the middle line is a
real share of the total and your prompts are big, try 1 hour for a few days and compare `/usage`.

**Or work out what the other limit would have cost.** The script I used for the numbers above is
[public as a gist](https://gist.github.com/omars-lab/4fc25fd8209d7b2199821ad84988a253). It needs
Node 20 and nothing else, reads the logs on the machine you run it on, and prints totals only. If
your logs ran at 5 minutes (an API key, or subagents), it answers "with 1 hour, you would have
saved N% of your budget". If they ran at 1 hour, it prices them at 5 minutes:

```bash
node cache-ttl-gaps.mjs --root ~/.claude --days 30
# logs too old to say 5m or 1h: add --ran-at 5m
```

## Why it works

- **The cost follows your pauses, not the setting.** The same 1-hour limit made no difference on my
  subscription and saved about a tenth at work. Only your own pause pattern says which.
- **A pause is cheap to measure.** Every request is already in your session logs with a time on it.
- **The break-even is simple.** 1 hour costs 0.75x more on what it writes and saves about 1.15x on
  each return after 5 to 60 minutes. If those returns are common next to how fast your
  conversation grows, 1 hour wins.
- **Subagents are a separate choice.** They work in fast bursts (99% of my subagent requests came
  within 5 minutes of the last), which is why they default to 5 minutes.
- **Waiting on a subagent is a pause too.** The main conversation's cache clock runs while a
  subagent works. Subagents that take 5 to 60 minutes favour 1 hour on the main conversation; ones
  that finish in under 5 minutes, or take over an hour, don't.
